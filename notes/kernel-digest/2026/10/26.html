[PATCH net v4 1/2] inet: reject unhashed sockets during established lookups ​

Hyunwoo Kim (imv4bel@gmail.com)｜netdev

TCP established ehash 查找是无锁的，且相关 socket 缓存使用 SLAB_TYPESAFE_BY_RCU，内存可能在 RCU 读者仍持有旧地址时被复用。__inet_lookup_established() 与 __inet6_lookup_established() 在元组匹配后取引用并重做元组检查，但没有检查新对象是否已 hashed，若地址被复用为同元组的 socket，就可能返回一个 nulls node 尚未插入哈希链的对象。补丁在取引用后增加 unhashed 检查，作者用 SYN cookie request socket 驱动复用复现了该问题。

学习价值：深入揭示了 SLAB_TYPESAFE_BY_RCU 下“地址复用 + 元组相同”的经典陷阱，是学习无锁哈希查找校验流程的必读案例。

[PATCH RFC net-next 1/5] tls: add HKDF-Expand-Label for the TLS 1.3 key schedule ​

Martin Belanger via B4 Relay (devnull+martin.nvme.dev.gmail.com@kernel.org)｜netdev

该 RFC 补丁为 kTLS 增加 HKDF-Expand-Label 辅助函数，用于 TLS 1.3 KeyUpdate 时由内核自行推导下一代的 traffic secret、key 与 IV（RFC 9846 第 7.2 节）。由于输入 traffic secret 本身已是伪随机密钥，无需 HKDF-Extract；每次输出不超过 Hash.length 字节，因此单次 HMAC（SHA-256 或 SHA-384）即可完成。

学习价值：适合想了解 TLS 1.3 密钥调度在核内实现边界（哪些步骤可下移到内核）的读者，也展示了内核密码库 API 的用法。

[PATCH RFC net-next 4/5] tls: send a KeyUpdate at the record limit and on request ​

Martin Belanger via B4 Relay (devnull+martin.nvme.dev.gmail.com@kernel.org)｜netdev

补丁在记录层实现 KeyUpdate 的发送时机：当密钥已保护约 2^24 条记录（AES-GCM 的用量上限为 2^24.5 条全尺寸记录）时，在下一记录之前发送 KeyUpdate，做法与 GnuTLS 一致；同时响应带 update_requested 的 KeyUpdate，且回复须在下一条 Application Data 记录之前发出。由于上限按记录计数，只有记录层知道记录边界，因此该逻辑必须放在记录层。

学习价值：清晰说明了 TLS 1.3 密钥用量限制为何必须由记录层而非密钥管理层执行，有助于理解 kTLS 的分层设计。

[PATCH RFC net-next 5/5] selftests/tls: add KeyUpdate tests ​

Martin Belanger via B4 Relay (devnull+martin.nvme.dev.gmail.com@kernel.org)｜netdev

该补丁为 selftests/tls 增加 KeyUpdate 测试，覆盖双向连接上两个 socket 均注册 traffic secret 的场景。测试项包括注册错误（长度错误、缺 key、TLS 1.2、SM4、RX secret 先于 TX secret 注册）、双向 KeyUpdate 及其前后数据、首次读取前排队的数据/KeyUpdate/数据序列、update_requested 的应答与串行化、跨 KeyUpdate 的 splice()，以及 TLS_TX 安装密钥后注册 secret 被清除等行为。

学习价值：是学习 kTLS 用户态测试框架与 TLS 1.3 状态机边界条件的实用参考。

[PATCH RFC net-next 2/5] tls: add socket options to register the traffic secrets ​

Martin Belanger via B4 Relay (devnull+martin.nvme.dev.gmail.com@kernel.org)｜netdev

kTLS 只保存每个方向的 key 与 IV，不保存其来源的 traffic secret，而推导是单向的，内核无法自行算出下一代密钥。补丁新增 TLS_TX_TRAFFIC_SECRET 与 TLS_RX_TRAFFIC_SECRET 两个 socket 选项，由 socket 所有者在安装密钥后传入 TLS 1.3 的 application traffic secret；哈希算法由已安装密钥的 cipher 决定，因此选项只需传 secret。未注册 secret 的 socket 行为保持不变，TX secret 可单独注册。

学习价值：展示了在不破坏既有 ABI 的前提下为 kTLS 扩展密钥管理能力的接口设计思路，值得关注 setsockopt 语义与兼容性处理。

[PATCH RFC net-next 3/5] tls: update the RX key when a KeyUpdate is received ​

Martin Belanger via B4 Relay (devnull+martin.nvme.dev.gmail.com@kernel.org)｜netdev

该补丁为 kTLS 增加 RX 方向的 TLS 1.3 KeyUpdate 处理：当收到 KeyUpdate 记录时，若 socket 注册了 RX secret，内核会自动派生并安装新密钥，而不是用 -EKEYEXPIRED 阻塞读取。这解决了 nvme-tcp、sunrpc 等内核用户无法安装新密钥导致连接停滞的问题。对于格式非法的 KeyUpdate（非独立记录、长度错误或 request_update 值无效）行为保持不变。

学习价值：展示了 kTLS 中密钥更新与 socket 读取路径（recvmsg/splice/read_sock）的交互机制，是理解内核 TLS offload 数据流的良好案例。

[PATCH bpf 2/2] selftests/bpf: Redirect a bare FIN to another socket's egress ​

Eli Skeggs via B4 Relay (devnull+kernel.eliskeggs.com@kernel.org)｜netdev
