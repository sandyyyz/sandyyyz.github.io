Ridger MIMO AI 原生存储系统技术分析 ​

1. 文档说明 ​

本文对 Ridger Company Limited 的 MIMO AI 原生存储系统进行技术总结。分析依据为已有产品介绍及前述讨论，重点覆盖总体架构、可能的技术实现、与相似技术路线的比较、产品结果判断，以及仍可质疑和继续深究的问题。

说明：本文将分析对象统一记为 MIMO。MMIO 通常表示 Memory-Mapped I/O，与本产品名称不是同一概念。

本文未获得 MIMO 的完整设计文档、源代码、兼容性矩阵和可复现测试报告。因此，除明确标注的产品公开信息外，底层实现细节属于依据公开架构描述作出的技术推断，不应视为厂商已经确认的事实。

2. 产品定位与总体判断 ​

MIMO 定位于中小规模 AI 集群、单台大型 GPU 服务器、边缘推理设备和桌面级 AI 工作站，主要通过 GPUDirect Storage、NFS over RDMA、用户态存储数据面和本地 NVMe SSD，缩短存储数据进入 GPU 显存的路径。

其核心架构取舍不是构建一个覆盖数百节点的通用分布式文件系统，而是主动缩小系统边界，减少跨节点网络、分布式元数据协调和多层内核 I/O 栈的开销，以换取较低延迟、较低 CPU 占用和较简单的部署形态。

可以将其核心目标概括为：

text
传统路径：
远端存储 -> 网络协议栈 -> 主机内存 -> CPU 协调/复制 -> GPU 显存

MIMO 目标路径：
NVMe 或远端文件服务 -> RDMA/GDS -> GPU 显存

3.1 接入层 ​

MIMO 使用 NFS 提供通用文件接口，减少 AI 应用迁移成本，同时使用 RDMA 替代传统 TCP 传输路径，以降低网络协议处理和 CPU 开销。对于支持 GDS 的应用，GPU buffer 可以参与直接 DMA，减少经主机内存 bounce buffer 中转的数据复制。

3.2 文件与元数据层 ​

如果产品对外提供标准文件语义，则必须维护目录、文件、权限、文件句柄、extent、属性缓存和一致性状态。Snapshot 和 Clone 通常需要采用 Copy-on-Write、引用计数或不可变 extent 等机制，以避免复制完整数据集。

3.3 数据布局与保护层 ​

产品描述中的用户态 FTL 更可能是软件定义的数据映射层，而不是 SSD 固件内部的 NAND FTL。该层可能将文件逻辑 extent 映射到 SSD、namespace 和 LBA，并实施条带化、空间分配、垃圾回收、快照引用管理和故障重建。

动态纠删码可能根据数据状态选择副本或不同的数据盘、校验盘比例。由于产品强调单机直连，该纠删码很可能主要保护同一设备内的多块 SSD 故障，而不能替代跨节点副本或整机级高可用。

3.4 用户态数据面 ​

用户态数据面可能采用轮询、每核独立队列、预分配 I/O 描述符、无锁消息传递和 NUMA 绑定。正常 I/O 尽量避免系统调用、上下文切换、共享锁和通用块层调度，从而降低平均延迟及尾延迟。

此设计的代价是占用专用 CPU 核、设备可能被用户态服务独占、故障恢复更复杂，并且需要自行实现完善的可观测性和运维能力。

4. 关键技术的可能实现 ​

4.1 GPUDirect Storage 数据路径 ​

GDS 的核心价值是允许本地或远端存储数据通过 DMA 更直接地进入 GPU 显存。完整路径仍需要 GPU 驱动、内存注册、文件系统、NIC 或 NVMe 设备和拓扑条件配合。

MIMO 在这一层可能需要实现：

  • GPU 显存注册以及注册缓存；
  • DMA-BUF 或其他 peer-memory 映射管理；
  • GPU 虚拟地址到 DMA scatter-gather list 的转换；
  • 文件 offset 到底层 extent 和 LBA 的快速映射；
  • GPU、NIC、NVMe 和 CPU 的 NUMA、PCIe 拓扑感知；
  • 非对齐 I/O、小 I/O 和不支持配置下的 fallback；
  • GPU reset、DMA 映射失效和短 I/O 的错误处理；
  • GDS 路径是否真正生效的监控，而不能仅以 API 调用成功作为判断依据。

4.2 NFS over RDMA ​

NFS over RDMA 保留 NFS 的文件访问模型，但将 RPC 数据传输建立在 RDMA 上。其优势是应用兼容性较好、CPU 消耗低于传统 TCP 路径，并能与远程 GDS 配合。

不过，RDMA 并不会消除 NFS 的全部语义开销。文件句柄检查、元数据查找、权限控制、客户端缓存一致性和 RPC 状态机仍然存在。因此，端到端延迟必须同时考虑协议、元数据和持久化语义，而不能仅以网络 RTT 衡量。

较合理的实现是以 extent 为粒度执行 Copy-on-Write：

快照   -> 引用 extent A、B、C
修改 B -> 分配新 extent B'

5. 与相似技术实现的比较 ​

SPDK构建高性能用户态存储应用的基础框架用户态 NVMe、轮询、无锁、每核线程、DMASPDK 主要提供块设备和存储服务基础设施，不直接提供完整 GPU 文件系统、快照、Clone 和 AI 数据平台

5.1 MIMO 与 SPDK 的关系 ​

MIMO 与 SPDK 共享用户态、轮询、零拷贝和 per-core queue 等设计原则，但两者层次不同。SPDK 是通用基础设施，MIMO 是面向特定工作负载的完整产品。

MIMO 有充分理由自研以下部分：

  • GPU buffer 注册、缓存和 DMA 映射；
  • GDS 与 NFS/RDMA 的端到端整合；
  • 文件元数据和 extent 映射；
  • Snapshot、Clone、EC 与重建；
  • GPU、NIC、NVMe 的拓扑感知调度；
  • 产品化管理、监控和故障处理。

但以下基础部分通常优先复用 SPDK 更合理：

  • NVMe Controller 初始化；
  • Admin Command 和 namespace 管理；
  • 标准 Queue Pair 生命周期；
  • VFIO/IOMMU 基础设施；
  • 超时、Abort、Reset 与热插拔；
  • 通用 DMA 内存管理和设备兼容处理。

如果 MIMO 从零重写这些底层能力，应证明 SPDK 的具体抽象导致了无法接受的拷贝、调度或尾延迟开销。否则，重写会显著增加设备兼容、异常恢复、数据正确性和长期维护风险。

6. 最终产品结果与适用边界 ​

6.1 可以合理预期的结果 ​

在单机或小规模环境中，如果 GPU、NIC 和 NVMe 拓扑合理，并且 GDS 没有 fallback，MIMO 可能取得以下实际收益：

  • 降低存储到 GPU 的数据搬运次数；
  • 降低主机 CPU 在数据复制和网络协议处理上的占用；
  • 提高大块顺序读写和并发读取吞吐；
  • 降低模型加载、训练样本读取和 Checkpoint 的等待时间；
  • 相比跨节点分布式文件系统获得更低的单次 I/O 延迟；
  • 通过 NFS 接口减少现有 AI 应用的改造成本。

6.2 公开指标的正确解读 ​

前述材料出现过约 40 至 90 微秒 的延迟描述，以及相对于分布式系统更低的延迟比较。这些数字目前只能视为产品宣称或特定测试条件下的结果，不能视为本文已经独立验证的实验结论。

若该延迟来自本地 NVMe、低队列深度、缓存命中、无保护或大块对齐 I/O，而对比对象是跨网络、带分布式元数据和容错语义的文件系统，则二者并非同口径比较。

6.3 适合的场景 ​

  • 单台多 GPU 服务器的高速容量扩展；
  • 中小规模训练集群；
  • 模型权重加载和推理冷启动；
  • 训练 Checkpoint；
  • RAG 索引和数据集批量读取；
  • 工业机器视觉、高频采集和边缘推理；
  • 需要本地部署和数据隐私的小团队 AI 工作站。

6.4 不适合或需要谨慎评估的场景 ​

  • 数百至数千 GPU 共享统一数据集；
  • PB 级容量和跨节点线性扩展；
  • 要求任意存储节点失效后服务连续可用；
  • 多租户隔离、配额和审计要求严格的云平台；
  • 依赖完整 Kubernetes CSI、跨站点复制和成熟生态的环境；
  • 不能接受用户态服务进程成为关键故障点的业务。

6.5 当前可形成的产品结论 ​

MIMO 的产品价值主要来自架构聚焦，而不只是采用了某一项新协议。该产品通过牺牲部分横向扩展能力和分布式故障域，换取更短的数据路径和更低的部署复杂度。这一取舍在中小规模 AI 场景中具有合理性。

但是，MIMO 是否构成成熟的企业级存储产品，取决于数据一致性、异常恢复、硬件兼容、长期尾延迟和运维能力，而不取决于正常路径上的最低延迟。

7. 可质疑或继续深究的关键问题 ​

7.1 关于架构和实现 ​

  1. 产品所谓“完全用户态”具体覆盖哪些模块？NVMe 驱动、RDMA transport、NFS server、文件系统和元数据服务是否都在用户态？
  2. 底层是否实际复用了 SPDK、DPDK、libfabric、rdma-core 或其他开源组件？若完全自研，具体替代了哪些模块？
  3. 为什么不能在 SPDK 上扩展 GPU buffer 支持？SPDK 的瓶颈是 Bdev 抽象、Reactor、内存模型，还是错误恢复框架？
  4. GPU 显存如何映射为 NVMe PRP/SGL 或 RDMA MR？是否使用 DMA-BUF？
  5. GPU、NIC 和 NVMe 不在同一 PCIe Root Complex 时如何处理？是否退回主机内存路径？
  6. 如何检测并公开显示 GDS 真实生效或 fallback？

7.2 关于文件系统语义 ​

  1. 是否完整支持 POSIX 语义，还是只支持适合 AI 负载的子集？
  2. rename、fsync、close、O_DIRECT、mmap 和文件锁的语义如何实现？
  3. NFS 使用哪个版本，NFSv3、NFSv4.1 还是 pNFS？
  4. 客户端缓存一致性、delegation 和多客户端写冲突如何处理？
  5. 元数据是单实例、主备还是分布式？元数据服务崩溃后如何恢复？

7.3 关于数据保护 ​

  1. “动态 EC”的具体策略是什么？不同工作负载使用何种数据盘和校验盘比例？
  2. 小块随机写是否触发 read-modify-write？
  3. 条带写入过程中掉电，如何避免 data/parity 不一致？
  4. EC 是机内多 SSD 保护还是跨设备保护？能否容忍整机故障？
  5. SSD 故障后的重建时间、读放大和 p99.9 延迟是多少？
  6. 是否具有端到端 checksum、静默数据损坏检测和周期性 scrub？
  7. 软件 FTL 与 SSD 内部 FTL 是否造成双重写放大和 GC 干扰？

7.4 关于性能结果 ​

  1. 40 至 90 微秒 是平均值、p50、p99 还是最小值？
  2. 测量起点和终点在哪里，是 NVMe 命令、NFS 请求、cuFile 调用还是完整应用操作？
  3. 是否包含 GPU 内存注册、网络传输、文件元数据和数据持久化？
  4. 测试块大小、读写比例、队列深度和并发客户端数是多少？
  5. 测试是热缓存还是冷数据？是否绕过了服务端 DRAM cache？
  6. Snapshot、Clone、EC 和后台重建开启后性能如何？
  7. 相比 SPDK 基线，性能改善来自哪里，改善幅度是多少？
  8. 相比 WEKA 或 VAST 时，是否使用相同硬件、网络、保护级别、请求模型和客户端数量？

7.5 关于可靠性与运维 ​

  1. 用户态进程崩溃后，NVMe Controller 和未完成 I/O 如何接管或恢复？
  2. 是否支持控制器 reset、PCIe AER、SSD 热拔插、namespace 变化和 RDMA 断链？
  3. 升级期间是否保持服务可用，元数据格式是否支持回滚？
  4. 是否具备故障注入、长稳测试和断电测试报告？
  5. 是否提供 Prometheus、日志追踪、慢 I/O 分析和 GDS fallback 指标？
  6. 兼容的 GPU、驱动、CUDA、内核、NIC 和 SSD 型号有哪些？

8. 建议的验证实验 ​

8.1 对照组 ​

建议至少建立以下三组：

text
A：Linux 内核文件系统 + 普通 NFS/TCP

9. 综合结论 ​

MIMO 的技术路径具有合理性：它面向中小规模 AI 基础设施，使用用户态数据面、RDMA、GDS 和本地 NVMe 缩短 GPU I/O 路径，并在上层提供文件访问、快照、克隆和数据保护。其差异化并非来自“用户态”或“零拷贝”这些已有思想，而来自 GPU、网络、文件语义、数据布局和运维能力的端到端整合。

MIMO 最值得重写和形成壁垒的是 GPU buffer 管理、GPU/NIC/NVMe 联合调度、文件 extent 映射、Snapshot、Clone、动态 EC 和故障恢复。对于 NVMe 初始化、VFIO、DMA 基础设施和标准错误处理，复用 SPDK 通常更具工程合理性。若选择完全重写，则应通过同硬件、同负载的基线测试证明 SPDK 的具体瓶颈及重写后的显著收益。

现阶段可以认为该产品具有明确的技术方向和适用市场，但尚不能根据宣传材料确认其端到端性能、完整 POSIX 语义、数据可靠性和企业级成熟度。最终判断应以可复现基准、真实 AI 应用收益、长稳运行和故障恢复结果为准。

Q&A ​

1、SPDK已经提供了成熟的用户态通用nvme访问框架，为什么不直接把它作为底层，而是选择完全重写?
SPDK诞生于2014年，SPDK作为知名大厂开源的性能开发套件，我们在2024年MIMO技术路线验证初期曾把它一个选项重点考虑和深入研究过，但由于MIMO是针对AI原生设计的存储系统，AI工作流中各个环节对存储系统的要求更为极致和不同，同时我们还有针对未来有更长远的构想和规划，除了高性能块服务，比如针对新一代文件系统、介质和语义的广泛支持方面我们都有更多的构想，我们不得不选择了从头开发，虽然工作量和难度进入一个更高的量级，但给我们留下了足够的灵活性和面向未来更长远的竞争力。从目前版本来看，mimo的一些特性比如本地纠删、ftl、gds原生支持、内存管理等都是spdk目前没有很好或根本没有实现的，随着后面下一代mimo 2.0的推出，就会发现mimo的架构和所能实现的特性是spdk完全所不能承载的。简单总结来说，spdk对我们的规划来说，还有有点老并且简陋，与其改造它还不如重新做。

2、架构图里的"自研数据管理层FTL"，是指在软件层也实现了一层FTL吗?如果是的话，它和底层firmware里的FTL如何协同工作，二者之间的一致性又如何保证?
MIMO的数据一致性和可靠性是靠底层mimofs和自有保护算法来保证的，不依赖底层具体部件的内部算法。 MIMO在系统级别的数据处理，包括ftl，页对齐、内存管理、动态放置和一致性保护算法方面，和单盘片内的算法包括FTL等完全不同，不是一个层面上的工作，两者间没有冲突和联动。虽然我们目前发售的版本不开放任意硬件兼容，但从技术角度来说，MIMO对于底层介质没有特别要求和侧重，不要求特定接口和协议，只要是General purposed ssd达到可靠性要求就可以，不依赖ZNS等特别版本ssd，也不锁定intel或现在solidiam ssd。 一句话说，MIMO只对前端GPU服务器负责，为了完成自己的工作需要在系统层面做好必要工作，而SSD内部的FTL是他自己的必要工作之一，作为部件之一需要对MIMO负责，而负责的标准就是普通业界标准。
